# Audit Report: Pare (NFL Team Comparison)

*Read-only audit per `AUDIT.md`. Nothing in the codebase was changed. The only file written is this report.*
*Date: 2026-10-01 · Reviewer: full-panel audit (architecture, security, data, QA, UX, iOS)*

---

## 1. Project Map

**What it is.** Pare is a production NFL team head-to-head stat-comparison web app (live at `pare.gg`, self-hosted on an M1 Mac mini under PM2), plus an in-progress SwiftUI/WKWebView iOS wrapper. Users land on a schedule-first home (weekly matchups), tap a matchup, and see a "theScore-style" inward-bar comparison of the two teams across offense/defense metrics, with standings and leaderboards tabs. It's a read-only, no-login, public data app.

**Stack (how detected).**
- Next.js 15.5.27 + React 19 + TypeScript 5.9 + Tailwind v3 — `package.json`, `next.config.ts`, `tsconfig.json`.
- App Router (server components + route handlers) — `app/` layout.
- Data: ESPN public JSON APIs (schedule, team stats, standings, leaderboards) + Sleeper (fantasy) — `lib/espn*.ts`, `lib/fantasy.ts`, `DATA_SOURCES.md`. The old PFR/CSV layer was removed (confirmed: `lib/pfrCsv.ts`/`data/pfr/` gone; `CLAUDE.md` flags itself partially stale).
- State: React context stores, no external state lib — `components/ComparisonsProvider.tsx`, `components/schedule/ScheduleProvider.tsx`. Persistence via `localStorage` — `lib/comparisons/persist.ts`.
- PWA service worker — `public/sw.js` (off by default; `NEXT_PUBLIC_ENABLE_SW=true` to enable).
- iOS: XcodeGen-managed SwiftUI + WKWebView wrapper — `ios/` (`project.yml`, `Pare/Web/*.swift`).

**Data flow.** ESPN/Sleeper → server-side fetch seams (`lib/espnStats.ts`, `lib/schedule.ts`, `lib/standings.ts`, `lib/leaders.ts`, `lib/fantasy.ts`, all with `next: { revalidate }` + in-memory/`unstable_cache` layers) → API route handlers (`app/api/**`) and server components → client hooks (`lib/useNflStats.ts`) → context providers → `ComparePane`/`DynamicComparisonRow` → client-side ranking (`useRanking`) + bar math (`useBarCalculation`). One client-side exception: `lib/hooks/useLiveScores.ts` polls ESPN's scoreboard **directly from the browser** every 15s while a game is live.

**Trust boundaries.** (1) Inbound HTTP to the route handlers — only `/api/schedule?week=N` takes a user param, and it's integer-validated (1–18). (2) Outbound fetches to ESPN/Sleeper — all URLs built from internal constants + numeric IDs or validated params (no user string flows into a URL). (3) `localStorage` reads — validated/versioned. (4) iOS JS↔Swift bridge — receives messages from the loaded web content only. There is no auth, no database, no user accounts, no uploads, no payments, no PII.

**Blast radius.** Low. Worst realistic case: ESPN changes/blocks its undocumented endpoints and the app degrades to fallbacks/"—" cells (it's engineered to never blank). No user data to lose, nothing to breach. The real exposure is **business/legal** (monetizing on unlicensed data — see 🟠 H1) and **the iOS release being misconfigured** (🟠 H2), not a classic security blast radius.

**Reviewed vs not reviewed.** Fully read: all config, all `app/api/**` route handlers, the entire `lib/` data + hooks layer, state stores + persistence, `utils/`, `public/sw.js`, root layout + error boundaries, `public/manifest.json`, the key render components (`DynamicComparisonRow`, `RankBadge`, `RankingDropdown`, `TeamLogo`, `useTheme`, `CompareWorkspace`, both providers), and the full iOS wrapper (`Info.plist`, xcconfig, `project.yml`, all `Web/` Swift, `Config.swift`, app entry). **Not individually read** (sampled/inferred from siblings): the remaining presentational components under `components/schedule/`, `components/mobile/`, `components/leaderboards/`, `components/compare/` (ComparePane, CompareQuadrants, CompareTabBar, etc.), `components/standings/`, and `lib/hooks/useGameSummary.ts` / `useIsMobile.ts` / `useOfflineStatus.ts` / `usePWA.ts` / `lib/standings` consumers. Node runtime behavior under real load, the actual PM2/Cloudflare-tunnel deployment, and ESPN's live responses were **not** executed (read-only audit) — findings that depend on them are marked *Needs verification*.

## 2. Executive Summary

Pare is a **well-built, genuinely professional hobby-scale codebase** — easily top-tier for a self-described "vibe coder." The data layer is the strongest part: timeouts on every outbound fetch, batched concurrency, graceful stale/empty fallbacks so the UI never blanks, an internal Σallowed==Σgained consistency check on the defense aggregation, versioned/guarded `localStorage`, and clean React hook hygiene (effect cleanup, memoization, SSR-safe hydration). **There are no critical security issues** — no secrets in the repo, no injection surface, no auth/PII/payment exposure (it's a read-only public app, so most of the scary categories simply don't apply, and I won't manufacture a 🔴 to pad the report).

The real issues are two **business/release blockers** and a handful of **correctness, logging, and hygiene** items: the data sources (ESPN unofficial + Sleeper non-commercial) aren't licensed for the planned ads/subscriptions, and the iOS release build points at a dead placeholder domain instead of `pare.gg`.

**Counts by severity:** 🔴 0  🟠 2  🟡 6  🔵 11  ⚪ (several observations)

**Fix first:** Before any monetization, resolve the data-source licensing (🟠 H1) — it's the one item with real downside (a cease-and-desist or App Store rejection) and it gates the whole revenue plan; everything else is a code fix you control.

## 3. Findings

### 🟠 HIGH

#### 🟠 H1 — Monetization plan rests on unlicensed data sources
- **Where:** `DATA_SOURCES.md`; `lib/espnStats.ts`, `lib/espnScoreboard.ts`, `lib/schedule.ts`, `lib/standings.ts`, `lib/leaders.ts` (ESPN); `lib/fantasy.ts` (Sleeper, `api.sleeper.app`).
- **What's wrong (plain language):** The whole app is powered by ESPN's *undocumented, unofficial* public endpoints and by Sleeper, whose free tier is **non-commercial only**. That's fine for a free hobby project — but the plan is to add ads + subscriptions. The moment money changes hands, "we're just a hobby" stops being the posture, and you're running a commercial product on data you don't have the right to resell, plus NFL team names/logos (trademarks).
- **The real term:** data-source **Terms-of-Service / licensing risk** + trademark use.
- **Why it matters:** Concrete downsides once you monetize: ESPN silently changes/blocks the endpoint (your app breaks), or sends a cease-and-desist; Apple rejects the App Store build for using NFL marks/ESPN data without rights; Sleeper's non-commercial clause is violated. This is the one finding that can end the project rather than just annoy a user.
- **How confident I am:** Confirmed as a risk (not legal advice). Your own `DATA_SOURCES.md` and project notes already flag it — this audit is agreeing and raising its priority given the monetization goal.
- **Suggested fix (described, not applied):** Keep free/hobby as-is. **Before** charging: move to a licensed commercial provider (Sportradar / SportsDataIO / API-Sports) for stats + schedule, and/or get Sleeper's commercial license; sort out NFL trademark use for names/logos; have a lawyer confirm. You've already abstracted the data layer behind clean seams (`lib/espnStats`, `lib/fantasy`, `lib/schedule`) — swapping providers is contained, which is exactly the right setup. Raw stats (numbers) are facts and free; the *API terms* and *logos* are the constraint.

#### 🟠 H2 — iOS release build points at a dead placeholder domain (not `pare.gg`)
- **Where:** `ios/Pare/Models/Config.swift:14` (`prodBaseURL = "https://pare-nfl.app"`); `ios/Config/Release.xcconfig` (`PROD_BASE_URL = https:/$()/pare-nfl.app`); `ios/Config/Debug.xcconfig` same.
- **What's wrong (plain language):** The production iOS build is hard-coded to load `https://pare-nfl.app`, which isn't your site — your live domain is `pare.gg`. A TestFlight/App Store build would launch into a blank/failed WebView. Worse, there are **two** sources of truth for the URL: the `.xcconfig` files define `PROD_BASE_URL`/`ACTIVE_BASE_URL`, but `Config.swift` *re-hardcodes* the same URLs in Swift and uses those via `#if DEBUG`, so the xcconfig values are effectively dead.
- **The real term:** configuration drift / dead configuration + wrong production endpoint.
- **Why it matters:** The iOS App Store launch is your stated #1 strategic goal. This guarantees a broken first build and wasted TestFlight cycles, and the duplicated config means a future "fix the URL" in the xcconfig won't take effect.
- **How confident I am:** Confirmed (the domain mismatch and the Swift-vs-xcconfig duplication are both in the files).
- **Suggested fix (described, not applied):** Set the prod URL to `https://pare.gg` in **one** place. Cleanest: have `Config.swift` read `ACTIVE_BASE_URL` from the build settings (Info.plist-injected from xcconfig) instead of hardcoding, so Debug→localhost / Release→pare.gg flows from the xcconfig you already set up. Quick stopgap: just correct the string in `Config.swift` and both xcconfigs. (Small, surgical.)

### 🟡 MEDIUM

#### 🟡 M1 — Wrong ordinal suffixes ("21th", "22th", "23th", "31th") shown to users
- **Where:** `lib/useRanking.ts` — `formatRank()` inside `useRanking` (~L135) **and** the duplicate inside `calculateBulkRanking` (~L210). Surfaces in `components/RankingDropdown.tsx` (badge + list) and `components/DynamicComparisonRow.tsx` (non-dropdown rank + the `sr-only` screen-reader text).
- **What's wrong (plain language):** The rank formatter only special-cases 1st/2nd/3rd, then slaps "th" on everything else — so ranks 21, 22, 23, 31 render as "21th / 22th / 23th / 31th". Meanwhile you already wrote a **correct** ordinal helper in `components/ui/RankBadge.tsx` (`ordinalSuffix()` handles the 11–13 and x1/x2/x3 rules). So the codebase has two implementations of the same thing and ships the broken one.
- **The real term:** ordinal-suffix bug + logic duplication (WET).
- **Why it matters:** NFL has 32 teams, so 21st/22nd/23rd/31st come up constantly — this is visible on-screen and read aloud by screen readers ("ranked T-21th out of 32 teams"). It's the kind of polish gap that reads as "hobby project," which is exactly the bar you said is non-negotiable.
- **How confident I am:** Confirmed.
- **Suggested fix (described, not applied):** Delete both `formatRank` copies in `useRanking.ts` and reuse the already-correct `ordinalSuffix()` from `RankBadge` (export it, or lift it into a shared `utils/ordinal.ts`). One fix, both call sites, no more divergence.

#### 🟡 M2 — Production console logging in a hot render path
- **Where:** `lib/useTheme.ts:~160` — `console.log(\`🎨 [USE-THEME] Current theme:\`, theme);` runs **ungated** (no `NODE_ENV` check) at the top of the hook body. `useTheme()` is called by every `DynamicComparisonRow`. Also ungated: `components/RankingDropdown.tsx` `handleTeamSelect` logs + the `[Diag:RankingDropdown]` effect on every open.
- **What's wrong (plain language):** Every comparison row logs the whole theme object to the console on every render, in production. With ~5 metrics × 2 panels × up to 8 tabs, that's dozens of console writes per render on real devices.
- **The real term:** logging in a hot path / observability noise (prod).
- **Why it matters:** Console spam in production hurts performance on low-end phones (your target is iPhone 14 Pro and down), buries real errors, and can leak internal shape. Most of your other logs are correctly gated behind `process.env.NODE_ENV !== 'production'` — these few slipped through.
- **How confident I am:** Confirmed (the `useTheme` log has no env guard).
- **Suggested fix (described, not applied):** Gate these behind the dev check you already use elsewhere, or route them through `utils/logger.ts` (whose `debug` is verbose-only). Quick, surgical.

#### 🟡 M3 — Defense bar math ignores metric context (latent inversion, currently masked)
- **Where:** `lib/useBarCalculation.ts:~55` — `if (panelType === 'defense') { [teamANum, teamBNum] = [teamBNum, teamANum]; }`.
- **What's wrong (plain language):** For defense, the bar widths are swapped so "lower = bigger bar." That's correct for *allowed* metrics (points/yards/3rd-down allowed — all of today's defaults). But it's applied to **every** defense metric unconditionally, keyed only off `panelType`. For defense metrics where *higher* is better (turnovers forced, interceptions made), the bigger bar would go to the *worse* team — and it would disagree with the rank badge next to it (`useRanking` *does* handle context correctly via `higherIsBetter`).
- **The real term:** business-logic/context bug in the visualization (bar vs rank disagreement).
- **Why it matters:** The inward bar is literally "the heart of the app." Right now the bug is **masked** because ESPN's defense feed only populates allowed-metrics (points/total/pass/rush yards/3rd-down) — the forced/made metrics come back empty and the bars are hidden. The moment you add turnovers-forced/INT data for defense (likely, as you fill gaps), the bars silently invert.
- **How confident I am:** Likely / latent — the inversion logic is confirmed in code; it's currently unreachable only because the data isn't populated. Verify by selecting a "forced/made" defense metric once that data exists.
- **Suggested fix (described, not applied):** Drive the bar's "lower is better" decision off the **same** context `DynamicComparisonRow` already computes (`higherIsBetter` = defense ? `!metric.higherIsBetter` : `metric.higherIsBetter`) and pass it into `useBarCalculation`, instead of swapping purely on `panelType`. Then bar and rank always agree.

#### 🟡 M4 — iOS App Transport Security is wide open for web content
- **Where:** `ios/Pare/Resources/Info.plist` — `NSAppTransportSecurity` → `NSAllowsArbitraryLoadsInWebContent = true` (and `NSAllowsLocalNetworking = true`).
- **What's wrong (plain language):** This tells iOS "let the WebView load content over insecure/arbitrary connections." It's a dev convenience (so the simulator can hit `http://localhost:4000`), but as written it ships to production too.
- **The real term:** ATS exception (`NSAllowsArbitraryLoadsInWebContent`).
- **Why it matters:** It weakens transport security for the shipped app and is something **App Review specifically scrutinizes** — you can be asked to justify it, which delays approval. Your prod site is HTTPS (`pare.gg`), so the release build doesn't need arbitrary loads at all.
- **How confident I am:** Confirmed.
- **Suggested fix (described, not applied):** Keep the localhost exception for Debug only (`NSAllowsLocalNetworking` is the narrower, acceptable one). For Release, drop `NSAllowsArbitraryLoadsInWebContent`. Since you have separate Debug/Release xcconfigs, scope the ATS dict per-configuration (or use a separate Info.plist key set) so prod ships locked down.

#### 🟡 M5 — Effectively no automated tests and no CI gate
- **Where:** `utils/__tests__/teamHelpers.test.ts` (the only "test" — it's a `console.log` script with no assertions and no test runner); no test framework in `package.json`; no `.github/` workflows; `npm run check` (`tsc --noEmit && eslint`) exists but is manual.
- **What's wrong (plain language):** The parts most likely to be silently wrong — the bar math, the ranking/tie logic, the ESPN→`TeamStats` mapping, the per-game transform — have no tests, and nothing runs lint/types automatically before a deploy. The one test file can't fail.
- **The real term:** missing test coverage on critical paths + no CI gating.
- **Why it matters:** M1 (ordinal) and M3 (defense bars) are exactly the class of bug a handful of unit tests would have caught. With a self-hosted PM2 deploy, a bad push goes straight to `pare.gg`.
- **How confident I am:** Confirmed.
- **Suggested fix (described, not applied):** Add a real runner (Vitest fits a Next/TS repo) and write pure-function tests first — `useRanking`/`calculateBulkRanking` (incl. ordinals + ties), `useBarCalculation` (incl. defense context), `teamDataTransform` per-game math, `lib/comparisons/store.ts`. Then a tiny GitHub Action (or a pre-deploy script on the Mac mini) running `npm run check` + tests. Start small; the pure logic is already nicely separated for it.

#### 🟡 M6 — Metric selector offers metrics that have no data (+ duplicate/ghost entries)
- **Where:** `lib/metricsConfig.ts` — `AVAILABLE_METRICS` marks ~25 metrics `availableInOffense/Defense: true`, but `lib/espnStats.ts` `ESPN_FIELD_MAP` only populates ~15. No ESPN source for `score_pct`, `exp_pts_tot`, `penalties`, `penalty_yds`/`penalties_yds`, `pen_fd`, `pass_net_yds_per_att`, `yds_per_play_offense`, `rush_yds_per_att`, `pass_fd`, `rush_fd`. Also duplicates: `penalty_yds` vs `penalties_yds` (two keys, same stat), and `penalty_first_down` is a copy of `penalties` (same `field: 'penalties'`, name "Penalties").
- **What's wrong (plain language):** A user can pick metrics that will always render "—" (the row code does guard missing values well), and `useRanking` still computes a rank off a `0` fallback for absent values, so a metric with no data can show teams "ranked" on all-zeros. Plus the registry has copy-paste ghosts.
- **The real term:** dead/unsupported config options + duplicated metric definitions.
- **Why it matters:** Mildly confusing UX (empty metrics in the picker) and a maintenance trap (fixing a penalty metric in one of the two entries misses the twin).
- **How confident I am:** Confirmed for the duplicates/ghosts; Likely for the UX impact (the `—` guard in `DynamicComparisonRow` softens it, but the selector still lists them).
- **Suggested fix (described, not applied):** Either hide metrics with no live data source from the selector (derive availability from what the data layer actually populates), or mark them clearly as unavailable. Delete the duplicate `penalty_first_down` and consolidate `penalty_yds`/`penalties_yds` to one key.

### 🔵 LOW

#### 🔵 L1 — API error responses leak internal error details to the client
- **Where:** `app/api/nfl-2025/offense/route.ts` & `defense/route.ts` — the 500 branch returns `{ message: errorMessage, details: { errorType: error.constructor.name } }`.
- **Plain language / why it matters:** On total failure the client gets the raw error message and the JS error class name. Low impact (public app, no secrets in these messages today), but it's needless internal exposure and could surface an ESPN URL. The page-level error boundaries (`app/error.tsx`, `global-error.tsx`) correctly *don't* leak — mirror that here.
- **Confidence:** Confirmed. **Fix:** return a generic message + `requestId`; keep the detail server-side in the log only.

#### 🔵 L2 — Theme is per-hook local state, so global theming can't actually work
- **Where:** `lib/useTheme.ts` uses a local `useState` per call; `components/ThemeCustomizer.tsx` presumably sets a theme, but each `DynamicComparisonRow` calls its own `useTheme()` with independent state (always defaults to `'default'`).
- **Plain language / why it matters:** There's no `ThemeProvider`/context, so a theme chosen in `ThemeCustomizer` can't reach the comparison rows — the customizer is effectively a dead control and every row is hard-locked to the default scheme. Given the app is dark-mode-only with a fixed look, this may be intended-dead code rather than a live feature.
- **Confidence:** Likely — *Needs verification* of how `ThemeCustomizer` is wired. **Fix:** either lift theme into a context provider, or delete the unused theme-customization surface to cut dead weight.

#### 🔵 L3 — Stale documentation and fallback data
- **Where:** `CLAUDE.md` (still contains PFR/CSV architecture sections — self-flagged stale at top); `public/manifest.json` ("real-time 2025 stats"); `lib/schedule.ts` `FALLBACK_WEEK`/`WEEK_DATE_RANGES`/`CURRENT_WEEK = 3` use 2025 dates while `APP_CONSTANTS.SEASON = 2026`.
- **Plain language / why it matters:** Docs that contradict the code mislead future-you and any agent. The schedule fallback (shown only when ESPN is down) would display 2025 Week 3 games as "this week." Low stakes (fallback-only), but it's drift. `docs/proposed/CLAUDE.lean.md` already exists as the corrected rewrite — adopt it.
- **Confidence:** Confirmed. **Fix:** replace `CLAUDE.md` with the lean version; fix the manifest string; refresh/clearly-label the fallback week.

#### 🔵 L4 — No Content-Security-Policy yet; inline scripts need it
- **Where:** `next.config.ts` (security headers set X-Frame-Options/nosniff/etc. but comment defers CSP + HSTS to "Cloudflare edge / later"); `app/layout.tsx` has two `dangerouslySetInnerHTML` inline scripts (viewport height + SW registration).
- **Plain language / why it matters:** No CSP means no defense-in-depth against injected scripts. The inline scripts are safe today (no user input; the SW flag is a build-time boolean), but they'll require `'unsafe-inline'` or a nonce when you do add a CSP. Low for a read-only app, worth doing before monetizing.
- **Confidence:** Confirmed. **Fix:** add a CSP (nonce-based, or hash the two inline scripts) at the Cloudflare edge or via `next.config` headers.

#### 🔵 L5 — Tailwind typography plugin loaded via `import()` (likely not loading)
- **Where:** `tailwind.config.js` — `plugins: [ import('@tailwindcss/typography'), function({addUtilities}){...} ]`.
- **Plain language / why it matters:** `import(...)` returns a Promise, not a Tailwind plugin, so the typography plugin is probably silently not applied (CommonJS config expects `require('@tailwindcss/typography')`). If you rely on `prose` classes anywhere they'd be missing.
- **Confidence:** Likely — *Needs verification* (check whether `prose` styles actually render). **Fix:** `require('@tailwindcss/typography')`.

#### 🔵 L6 — RankingDropdown uses emojis, against the stated no-emoji design direction
- **Where:** `components/RankingDropdown.tsx` — `getRankEmoji` (🥇🥈🥉🔸) and the 📊 "Avg" badge.
- **Plain language / why it matters:** The Sleeper-tier redesign direction was explicitly "zero emoji in UI," and you built a custom emoji-free `RankBadge` for exactly this. This older dropdown still ships emoji rank markers, so the UI is inconsistent.
- **Confidence:** Confirmed. **Fix:** replace the emoji markers with `RankBadge` (which also fixes M1 here for free).

#### 🔵 L7 — Deprecated `String.prototype.substr`
- **Where:** `utils/helpers.ts` `generateRequestId()`; `lib/useNflStats.ts` request-id generation.
- **Plain language / why it matters:** `substr` is deprecated. Harmless today, trivial cleanup. **Fix:** `.slice(2, 11)` or `crypto.randomUUID()`. Confidence: Confirmed.

#### 🔵 L8 — iOS bridge `clearCache` wipes all website data, callable from any in-WebView JS
- **Where:** `ios/Pare/Web/PareBridge.swift` — `clearWebCache()` calls `removeData(ofTypes: allWebsiteDataTypes(), modifiedSince: 1970)` on `window.PareBridge.clearCache()`.
- **Plain language / why it matters:** Any script running in the WebView can nuke all cached web data with no confirmation. Low risk because the WebView only loads your own trusted site and external links go to Safari — but if `pare.gg` ever had an XSS, this is a free foot-gun. **Fix:** scope what's cleared, or require a native confirmation. Confidence: Confirmed (low severity).

#### 🔵 L9 — PWA manifest icon set is one 192px file wearing many hats
- **Where:** `public/manifest.json` — the same `/icon-192.png` is declared as 192, 512, maskable, and a 1280×720 screenshot.
- **Plain language / why it matters:** Android install / splash / maskable will look low-res or cropped wrong; the "screenshot" isn't one. Cosmetic, but it undercuts the premium bar. **Fix:** generate real 192/512/maskable icons + a true screenshot. Confidence: Confirmed.

#### 🔵 L10 — Defense yards aggregation is cheap when warm, heavy when cold
- **Where:** `lib/espnStats.ts` `_fetchDefenseYardsAllowed()` — fetches every completed game's box score up to the current week (batched 8-wide), then `unstable_cache`s the result 1h.
- **Plain language / why it matters:** At Week 18 a cold cache miss is ~250+ ESPN summary fetches in one request — slow cold responses and a burst of load on ESPN's endpoints (ties into H1's ban risk). It's cached, batched, and degrades gracefully, so it's not on fire; just worth knowing the cost grows through the season. **Fix:** cache per-week partials (completed weeks never change) and only fetch the current week on refresh. Confidence: Confirmed (perf characteristic) / *Needs verification* under real load.

#### 🔵 L11 — `addComparison` reads a value mutated inside a setState updater
- **Where:** `components/ComparisonsProvider.tsx` `addComparison` — `let added` is set inside the `setComparisons(prev => ...)` updater and read right after.
- **Plain language / why it matters:** Relies on React running the updater synchronously during dispatch; it works in practice but is a fragile pattern (updaters are meant to be pure). **Fix:** compute `added` from `prev.length < MAX` before calling setState, or derive it outside the updater. Confidence: Confirmed (low).

### ⚪ INFO / observations

Harmless at runtime, but the interface describes a contract that doesn't exist. (EE)

## 4. What's Actually Good (don't waste effort here)

- **Resilience/fallbacks are excellent.** Every outbound fetch has an `AbortController` timeout; failures degrade to stale cache → empty "—" rows → hardcoded fallback week, so the UI never blanks (`lib/espnStats.ts`, `lib/schedule.ts`, `app/api/**`). This is better than a lot of production apps.
- **The defense aggregation is thoughtful** — opponent box-score summation with an internal Σallowed==Σgained consistency assertion that needs no external source to validate.
- **React hygiene is solid** — effect cleanup (`useLiveScores` clears intervals/listeners/aborts; `WebViewContainer` removes KVO observers in `dismantleUIView`), memoization with stabilized primitive deps to make it actually hit, SSR-safe hydration (seed-then-restore, zero hydration mismatch in `ComparisonsProvider`).
- **`localStorage` persistence is defensively correct** — versioned schema, per-field validation, try/catch everywhere, trims to cap, repairs dangling `activeId` (`lib/comparisons/persist.ts`).
- **Clean separation + security basics** — pure data seams (`lib/espnScoreboard.ts` is client-safe and single-sourced), no secrets in the repo, `.env*` git-ignored, baseline security headers set, input validation on the one user-facing param, error boundaries that don't leak.
- **`RankBadge` is the model to copy** — correct ordinals, tie-aware tiers, graceful unranked handling. It's what the rest of the rank code should defer to.

## 5. Proposed Fix Plan

### Wave 1 — Stop the bleeding (🔴 Critical)
None. There are no critical issues. (Stated honestly, not padded.)

### Wave 2 — Shore it up (🟠 High) — do these before monetizing / before the next iOS build
1. **H1 — Data licensing.** Decide the commercial-data path (licensed provider and/or Sleeper commercial license) + NFL trademark handling **before** turning on ads/subs. *Big / needs discussion (and a lawyer). Blocks monetization, not current operation.*
